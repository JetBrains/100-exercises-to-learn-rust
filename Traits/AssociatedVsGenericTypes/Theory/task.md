## Generics та асоційовані типи

Ще раз погляньмо на визначення двох traits, які ми вже вивчили, — `From` і `Deref`:

```rust
pub trait From<T> {
    fn from(value: T) -> Self;
}

pub trait Deref {
    type Target;
    
    fn deref(&self) -> &Self::Target;
}
```

Обидва мають type parameters.\
У випадку `From` це generic parameter (узагальнений параметр) `T`.\
У випадку `Deref` це асоційований тип (associated type) `Target`.

У чому різниця? Коли варто обрати одне, а коли інше?

## Щонайбільше одна реалізація

Через те, як працює deref coercion, для заданого типу може існувати лише один
«цільовий» тип. Наприклад, `String` можна розіменувати лише в `str`.
Ідеться про уникнення неоднозначності: якби `Deref` можна було реалізувати для типу кілька разів,
який тип `Target` мав би обрати компілятор, коли ви викликаєте метод, що приймає `&self`?

Саме тому `Deref` використовує асоційований тип `Target`.\
Асоційований тип однозначно визначається **реалізацією trait**.
Оскільки `Deref` не можна реалізувати більше одного разу, для заданого типу ви зможете вказати лише один `Target`,
і жодної неоднозначності не виникне.

## Generic traits

З іншого боку, `From` можна реалізувати для типу кілька разів, **якщо вхідний тип `T` щоразу інший**.
Наприклад, можна реалізувати `From` для `WrappingU32`, використавши як вхідні типи і `u32`, і `u16`:

```rust
impl From<u32> for WrappingU32 {
    fn from(value: u32) -> Self {
        WrappingU32 { inner: value }
    }
}

impl From<u16> for WrappingU32 {
    fn from(value: u16) -> Self {
        WrappingU32 { inner: value.into() }
    }
}
```

Це працює, тому що `From<u16>` і `From<u32>` вважаються **різними traits**.\
Неоднозначності немає: компілятор може визначити, яку реалізацію використати, за типом значення, яке перетворюють.

## Розбір прикладу: `Add`

Наостанок розгляньмо trait `Add` зі стандартної бібліотеки:

```rust
pub trait Add<RHS = Self> {
    type Output;
    
    fn add(self, rhs: RHS) -> Self::Output;
}
```

Він використовує обидва механізми:

- має generic parameter `RHS` (right-hand side — права частина виразу), який за замовчуванням дорівнює `Self`;
- має асоційований тип `Output` — тип результату додавання.

### `RHS`

`RHS` — це generic parameter, завдяки якому можна додавати одне до одного значення різних типів.\
Наприклад, у стандартній бібліотеці ви знайдете такі дві реалізації:

```rust
impl Add<u32> for u32 {
    type Output = u32;
    
    fn add(self, rhs: u32) -> u32 {
      //                      ^^^
      // Замість цього можна було б написати `Self::Output`.
      // Компілятору байдуже, головне, щоб тип, який ви
      // вказуєте тут, збігався з типом, який ви призначили для `Output`
      // трохи вище.
      // [...]
    }
}

impl Add<&u32> for u32 {
    type Output = u32;
    
    fn add(self, rhs: &u32) -> u32 {
        // [...]
    }
}
```

Завдяки цьому компілюється такий код:

```rust
let x = 5u32 + &5u32 + 6u32;
```

тому що `u32` реалізує `Add<&u32>`, _а також_ `Add<u32>`.

### `Output`

`Output` — це тип результату додавання.

Навіщо взагалі потрібен `Output`? Хіба не можна просто використати як результат `Self`, тобто тип, що реалізує `Add`?
Можна, але це обмежило б гнучкість trait. Наприклад, у стандартній бібліотеці є
така реалізація:

```rust
impl Add<&u32> for &u32 {
    type Output = u32;

    fn add(self, rhs: &u32) -> u32 {
        // [...]
    }
}
```

Trait тут реалізовано для типу `&u32`, але результат додавання має тип `u32`.\
Таку реалізацію було б неможливо написати, якби `add` мав повертати `Self`, тобто в цьому випадку `&u32`.
`Output` дає змогу `std` відокремити тип, що реалізує trait, від типу результату й таким чином підтримати цей випадок.

> 💡 **Примітка**
>
> Гнучкість рідко буває безкоштовною: через `Output` визначення trait складніше, а тим, хто реалізує trait, доводиться
> вирішувати, що саме повертати. Такий компроміс виправданий, лише якщо ця гнучкість справді потрібна. Пам'ятайте про це,
> коли проєктуєте власні traits.

З іншого боку, `Output` не може бути generic parameter. Тип результату операції **мусить** однозначно визначатися,
щойно відомі типи операндів. Саме тому це асоційований тип: для заданої комбінації типу, що реалізує trait,
і generic parameters існує лише один тип `Output`.

## Висновок

Підсумуймо:

- Використовуйте **асоційований тип**, коли тип має однозначно визначатися для конкретної реалізації trait.
- Використовуйте **generic parameter**, коли хочете дозволити кілька реалізацій trait для одного й того самого
  типу з різними вхідними типами.
