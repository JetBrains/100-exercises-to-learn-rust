## Не блокуйте runtime

Повернімося до yield points.\
На відміну від потоків (threads), **tasks** **у Rust не можна витіснити** (preempt).

`tokio` не може самостійно вирішити призупинити task і запустити замість нього інший.
Керування повертається до executor **лише** тоді, коли task сам його віддає (yield), тобто
коли `Future::poll` повертає `Poll::Pending` або, у випадку `async fn`, коли
ви робите `.await` для future.

Через це runtime наражається на ризик: якщо task ніколи не віддає керування,
runtime ніколи не зможе запустити інший task. Це називається **блокуванням runtime** (blocking the runtime).

## Що таке блокування?

Скільки — це вже забагато? Скільки часу task може працювати, не віддаючи керування, перш ніж
це стане проблемою?  

Це залежить від runtime, застосунку, кількості tasks, що виконуються, і
багатьох інших чинників. Але загальне емпіричне правило таке: намагайтеся витрачати менш ніж 100
мікросекунд між yield points.

## Наслідки

Блокування runtime може призвести до:

- **Deadlocks** (потоки або tasks чекають один на одного й не можуть продовжити): якщо task, який не віддає керування, чекає на завершення
  іншого task, а той чекає, поки перший віддасть керування, виникає deadlock.
  Жодного поступу не буде, якщо тільки runtime не зможе запланувати інший task
  в іншому потоці.
- **Starvation** (голодування): інші tasks можуть узагалі не отримати змоги виконатися або виконатися
  з великою затримкою, що може призвести до низької продуктивності, наприклад до високих tail latencies.

## Блокування не завжди очевидне

Деяких типів операцій в асинхронному коді загалом варто уникати, як-от:

- Синхронного введення-виведення (I/O). Неможливо передбачити, скільки воно триватиме, і, найімовірніше,
  це буде довше за 100 мікросекунд.
- Ресурсоємних обчислень, що навантажують процесор (CPU-bound).

Однак друга категорія не завжди очевидна. Наприклад, сортування вектора з
кількох елементів — не проблема; але оцінка змінюється, якщо у векторі мільярди
елементів.

## Як уникнути блокування

Гаразд, то як уникнути блокування runtime, якщо ви _мусите_ виконати операцію,
яка є блокувальною або ризикує такою виявитися?\
Потрібно перенести роботу в інший потік. При цьому не варто використовувати так звані
потоки runtime — ті, у яких `tokio` виконує tasks.

Для цього `tokio` надає окремий пул потоків, який називається **блокувальним пулом** (blocking pool).
Запустити (spawn) синхронну операцію в блокувальному пулі можна за допомогою функції
`tokio::task::spawn_blocking`. `spawn_blocking` повертає future, який після завершення операції
дає її результат.

```rust
use tokio::task;

fn expensive_computation() -> u64 {
    // [...]
}

async fn run() {
    let handle = task::spawn_blocking(expensive_computation);
    // Тим часом робимо щось інше
    let result = handle.await.unwrap();
}
```

Блокувальний пул живе довго. `spawn_blocking` має працювати швидше,
ніж безпосереднє створення нового потоку через `std::thread::spawn`,
бо вартість ініціалізації потоку амортизується на багато викликів.
