## Ownership

Якщо ви розв'язали попередню вправу, спираючись лише на те, чого курс навчив вас досі,
ваші accessor methods, найімовірніше, мають такий вигляд:

```rust
impl Ticket {
    pub fn title(self) -> String {
        self.title
    }

    pub fn description(self) -> String {
        self.description
    }

    pub fn status(self) -> String {
        self.status
    }
}
```

Ці методи компілюються, і їх достатньо, щоб тести пройшли, але в реальних умовах із ними далеко не заїдете.
Розгляньмо такий фрагмент:

```rust
if ticket.status() == "To-Do" {
    // Макрос `println!` ми ще не розглядали,
    // але поки що досить знати, що він виводить
    // (шаблонне) повідомлення в консоль
    println!("Your next task is: {}", ticket.title());
}
```

Якщо спробувати його скомпілювати, ви отримаєте помилку:

```text
error[E0382]: use of moved value: `ticket`
  --> src/main.rs:30:43
   |
25 |     let ticket = Ticket::new(/* */);
   |         ------ move occurs because `ticket` has type `Ticket`, 
   |                which does not implement the `Copy` trait
26 |     if ticket.status() == "To-Do" {
   |               -------- `ticket` moved due to this method call
...
30 |         println!("Your next task is: {}", ticket.title());
   |                                           ^^^^^^ 
   |                                value used here after move
   |
note: `Ticket::status` takes ownership of the receiver `self`, 
      which moves `ticket`
  --> src/main.rs:12:23
   |
12 |         pub fn status(self) -> String {
   |                       ^^^^
```

Вітаємо, це ваша перша помилка від borrow checker (механізму перевірки запозичень)!

## Переваги системи ownership у Rust

Систему ownership у Rust спроєктовано так, щоб гарантувати, що:

- Дані ніколи не змінюються, поки їх читають
- Дані ніколи не читаються, поки їх змінюють
- До даних ніколи не звертаються після того, як їх знищено

За дотриманням цих обмежень стежить **borrow checker** — підсистема компілятора Rust,
що часто стає героєм жартів і мемів у спільноті Rust.

Ownership — ключова концепція Rust, і саме вона робить мову унікальною.
Завдяки ownership Rust забезпечує **безпеку пам'яті без шкоди для продуктивності**.
Для Rust одночасно справджується все наведене нижче:

1. Немає збирача сміття, який працює під час виконання програми
2. Вам як розробникові рідко доводиться керувати пам'яттю напряму
3. Неможливо спричинити dangling pointers (висячі вказівники), double free (подвійне звільнення пам'яті) та інші помилки, пов'язані з пам'яттю

Мови на кшталт Python, JavaScript і Java дають вам 2. і 3., але не 1.\
Мови на кшталт C чи C++ дають вам 1., але ні 2., ні 3.

Залежно від вашого досвіду, пункт 3 може звучати дещо загадково: що таке «dangling pointer»?
Що таке «double free»? Чим вони небезпечні?\
Не хвилюйтеся: ми детальніше розглянемо ці поняття далі в курсі.

А поки що зосередьмося на тому, як працювати в межах системи ownership у Rust.

## Owner

У Rust кожне значення має **owner** (власника), якого визначено статично, на етапі компіляції.
У будь-який момент часу в кожного значення лише один owner.

## Move semantics

Ownership можна передавати.

Наприклад, якщо ви володієте значенням, то можете передати ownership іншій змінній:

```rust
let a = "hello, world".to_string(); // <- `a` — owner цього String
let b = a;  // <- тепер owner цього String — `b`
```

Система ownership у Rust вбудована в систему типів: кожна функція має оголосити у своїй сигнатурі,
_як_ вона збирається взаємодіяти зі своїми аргументами.

Досі всі наші методи й функції **поглинали** (consume) свої аргументи: вони брали ownership над ними.
Наприклад:

```rust
impl Ticket {
    pub fn description(self) -> String {
        self.description
    }
}
```

`Ticket::description` бере ownership над екземпляром `Ticket`, на якому його викликають.\
Це називається **move semantics** (семантика переміщення): ownership значення (`self`) **переміщується** (move) від коду,
що викликає метод, до самого методу, і код, що викликав метод, більше не може використовувати це значення.

Саме цими термінами послуговується компілятор у повідомленні про помилку, яке ми бачили раніше:

```text
error[E0382]: use of moved value: `ticket`
  --> src/main.rs:30:43
   |
25 |     let ticket = Ticket::new(/* */);
   |         ------ move occurs because `ticket` has type `Ticket`, 
   |                which does not implement the `Copy` trait
26 |     if ticket.status() == "To-Do" {
   |               -------- `ticket` moved due to this method call
...
30 |         println!("Your next task is: {}", ticket.title());
   |                                           ^^^^^^ 
   |                                 value used here after move
   |
note: `Ticket::status` takes ownership of the receiver `self`, 
      which moves `ticket`
  --> src/main.rs:12:23
   |
12 |         pub fn status(self) -> String {
   |                       ^^^^
```

Зокрема, коли ми викликаємо `ticket.status()`, відбувається така послідовність подій:

- `Ticket::status` бере ownership над екземпляром `Ticket`
- `Ticket::status` витягує `status` із `self` і передає ownership `status` назад коду, що викликав метод
- Решта екземпляра `Ticket` (`title` і `description`) відкидається

Коли ми намагаємося знову використати `ticket` через `ticket.title()`, компілятор скаржиться: значення `ticket` уже немає,
ми ним більше не володіємо, а отже, не можемо його використовувати.

Щоб створити _корисні_ accessor methods, нам потрібно почати працювати з **references**.

## Borrowing

Бажано мати методи, які можуть читати значення змінної, не беручи ownership над ним.\
Інакше можливості програмування були б досить обмеженими. У Rust для цього існує **borrowing**.

Щоразу, коли ви позичаєте (borrow) значення, ви отримуєте **reference** на нього.\
References бувають двох видів залежно від привілеїв:

- Immutable references (`&`) дають змогу читати значення, але не змінювати його
- Mutable references (`&mut`) дають змогу і читати, і змінювати значення

> 💡 **Примітка**
>
> Це чудова ментальна модель для початку, але вона не відображає _повної_ картини.
> Ми уточнимо наше розуміння references [далі в курсі](../../../Threads/InteriorMutability/Theory/task.md).

Повернімося до цілей системи ownership у Rust:

- Дані ніколи не змінюються, поки їх читають
- Дані ніколи не читаються, поки їх змінюють

Щоб гарантувати ці дві властивості, Rust мусить запровадити певні обмеження на references:

- Не можна одночасно мати mutable reference та immutable reference на те саме значення
- Не можна одночасно мати більше ніж один mutable reference на те саме значення
- Owner не може змінювати значення, поки воно позичене
- Immutable references може бути скільки завгодно, доки немає жодного mutable reference

У певному сенсі immutable reference можна уявляти як lock (блокування) значення «лише для читання»,
а mutable reference — як lock «для читання й запису».

Дотримання всіх цих обмежень перевіряє borrow checker на етапі компіляції.

### Синтаксис

Як же на практиці позичити значення?\
Додаючи `&` або `&mut` **перед змінною**, ви позичаєте її значення.
Але будьте уважні! Ті самі символи (`&` і `&mut`) **перед типом** мають інше значення:
вони позначають інший тип — reference на вихідний тип.

Наприклад:

```rust
struct Configuration {
    version: u32,
    active: bool,
}

fn main() {
    let config = Configuration {
        version: 1,
        active: true,
    };
    // `b` — це reference на поле `version` змінної `config`.
    // Тип `b` — `&u32`, оскільки `b` містить reference на
    // значення типу `u32`.
    // Ми створюємо reference, позичаючи `config.version` за допомогою
    // оператора `&`.
    // Той самий символ (`&`), але інше значення залежно від контексту!
    let b: &u32 = &config.version;
    //     ^ Анотація типу тут не обов'язкова,
    //       вона лише пояснює, що відбувається
}
```

Те саме стосується аргументів функцій і типів значень, які вони повертають:

```rust
// `f` приймає як аргумент mutable reference на `u32`,
// прив'язаний до імені `number`
fn f(number: &mut u32) -> &u32 {
    // [...]
}
```
