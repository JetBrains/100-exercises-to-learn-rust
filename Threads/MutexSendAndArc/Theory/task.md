## Locks, `Send` і `Arc`

Стратегія часткового оновлення, яку ви щойно реалізували, має суттєвий недолік: у ній можливий race condition (результат залежить від порядку виконання потоків).\
Якщо два клієнти надішлють patches (патчі) для одного тікета приблизно одночасно, сервер застосує їх у довільному порядку.
Чий patch потрапить у чергу останнім, той і перезапише зміни, зроблені іншим клієнтом.

## Номери версій

Це можна спробувати виправити за допомогою **номера версії**.\
Під час створення кожен тікет отримує номер версії, що дорівнює `0`.\
Надсилаючи patch, клієнт має разом із бажаними змінами вказати поточний номер версії тікета.
Сервер застосує patch, лише якщо цей номер збігається з номером версії, який зберігається в нього.

В описаному вище сценарії сервер відхилив би другий patch: перший patch збільшив би номер версії, тож той
уже не збігався б із номером, який надіслав другий клієнт.

Такий підхід досить поширений у розподілених системах (наприклад, коли клієнт і сервери не мають спільної пам'яті),
і він відомий як **optimistic concurrency control** (оптимістичне керування паралельним доступом).\
Ідея в тому, що здебільшого конфліктів не виникає, тож можна оптимізувати систему під типовий випадок.
Ви вже достатньо знаєте Rust, щоб за бажання самостійно реалізувати цю стратегію як додаткову вправу.

## Блокування

Race condition можна усунути й інакше — запровадивши **lock** (блокування).\
Щоразу, коли клієнт хоче оновити тікет, він спершу має захопити lock цього тікета. Поки lock активний,
жоден інший клієнт не може змінити тікет.

Стандартна бібліотека Rust надає два різні примітиви блокування: `Mutex<T>` і `RwLock<T>`.\
Почнімо з `Mutex<T>`. Його назва походить від **mut**ual **ex**clusion (взаємне виключення), і це найпростіший вид lock:
лише один потік може звертатися до даних, незалежно від того, читає він їх чи записує.

`Mutex<T>` обгортає дані, які захищає, тому він generic за типом цих даних.\
Звернутися до даних напряму не можна: система типів змушує спершу захопити lock за допомогою `Mutex::lock` або
`Mutex::try_lock`. Перший метод блокує потік, доки lock не буде захоплено, а другий одразу повертає помилку, якщо
захопити lock не вдається.\
Обидва методи повертають guard (об'єкт-охоронець), який розіменовується в захищені дані й дає змогу їх змінювати. Lock звільняється,
коли guard знищують.

```rust
use std::sync::Mutex;

// Ціле число під захистом mutex
let lock = Mutex::new(0);

// Захоплюємо lock на mutex
let mut guard = lock.lock().unwrap();

// Змінюємо дані через guard,
// користуючись його реалізацією `Deref`
*guard += 1;

// Lock звільняється, коли `data` виходить за межі scope.
// Це можна зробити явно, знищивши guard,
// або це станеться неявно, коли guard вийде за межі scope
drop(guard)
```

## Гранулярність блокування

Що саме має обгортати наш `Mutex`?\
Найпростіший варіант — обгорнути весь `TicketStore` одним `Mutex`.\
Це спрацює, але суттєво обмежить продуктивність системи: ви не зможете читати тікети паралельно,
бо кожне читання муситиме чекати, доки lock звільниться.\
Це називають **coarse-grained locking** (грубозернистим блокуванням).

Краще використати **fine-grained locking** (дрібнозернисте блокування), коли кожен тікет захищений власним lock.
Тоді клієнти можуть і далі працювати з тікетами паралельно, якщо тільки вони не намагаються звернутися до одного й того самого тікета.

```rust
// Нова структура з окремим lock для кожного тікета
struct TicketStore {
    tickets: BTreeMap<TicketId, Mutex<Ticket>>,
}
```

Цей підхід ефективніший, але має недолік: `TicketStore` тепер має **знати** про багатопотокову
природу системи, тоді як досі `TicketStore` безтурботно ігнорував існування потоків.\
Та все одно спробуймо.

## Хто тримає lock?

Щоб уся схема працювала, lock треба передати клієнтові, який хоче змінити тікет.\
Тоді клієнт зможе змінювати тікет напряму (ніби в нього є `&mut Ticket`), а закінчивши — звільнити lock.

Тут не все так просто.\
Ми не можемо надіслати `Mutex<Ticket>` каналом, бо `Mutex` не реалізує `Clone`, а
перемістити його з `TicketStore` ми не можемо. Може, натомість надіслати `MutexGuard`?

Перевірмо цю ідею на невеликому прикладі:

```rust
use std::thread::spawn;
use std::sync::Mutex;
use std::sync::mpsc::sync_channel;

fn main() {
    let lock = Mutex::new(0);
    let (sender, receiver) = sync_channel(1);
    let guard = lock.lock().unwrap();

    spawn(move || {
        receiver.recv().unwrap();
    });

    // Пробуємо надіслати guard каналом
    // в інший потік
    sender.send(guard);
}
```

Компілятору цей код не подобається:


`MutexGuard<'_, i32>` не є `Send` — що це означає?

## `Send`

`Send` — це marker trait (trait без методів, що позначає властивість типу): він вказує, що значення цього типу можна безпечно передавати з одного потоку в інший.\
Крім того, `Send` — auto trait, так само як `Sized`: компілятор автоматично реалізує (або не реалізує) його для вашого типу
на основі визначення цього типу.\
`Send` можна реалізувати для своїх типів і вручну, але для цього потрібен `unsafe`, адже ви берете на себе гарантію, що
тип справді безпечно передавати між потоками, хоча компілятор не може перевірити цього автоматично.

### Вимоги каналів

`Sender<T>`, `SyncSender<T>` і `Receiver<T>` є `Send` тоді й лише тоді, коли `T` є `Send`.\
Річ у тім, що вони слугують для передавання значень між потоками, і якщо саме значення не є `Send`, передавати його
між потоками було б небезпечно.

### `MutexGuard`

`MutexGuard` не є `Send`, бо примітиви операційної системи, на яких `Mutex` реалізує
lock, вимагають (на деяких платформах), щоб той самий потік, який захопив lock, його й звільняв.\
Якби ми надіслали `MutexGuard` в інший потік, то звільняти lock довелося б уже іншому потоку, а це призвело б
до undefined behavior (поведінка, яку мова не визначає й не гарантує).

## Наші труднощі

Підсумуймо:

- Ми не можемо надіслати `MutexGuard` каналом. Тож не можна захопити lock на боці сервера, а потім змінити тікет на
  боці клієнта.
- Ми можемо надіслати `Mutex` каналом, бо він є `Send`, якщо дані, які він захищає, є `Send`, а для `Ticket` це
  так.
  Водночас ми не можемо ані перемістити `Mutex` із `TicketStore`, ані клонувати його.

Як розв'язати цю головоломку?\
Треба поглянути на проблему під іншим кутом.
Щоб заблокувати `Mutex`, не потрібне owned value. Досить shared reference (спільне посилання), бо `Mutex` використовує interior mutability (можливість змінювати дані через shared reference):

```rust
impl<T> Mutex<T> {
    // `&self`, а не `self`!
    pub fn lock(&self) -> LockResult<MutexGuard<'_, T>> {
        // Деталі реалізації
    }
}
```

Отже, клієнтові досить надіслати shared reference.\
Проте напряму цього зробити не вийде, бо reference мав би бути `'static`, а це не так.\
У певному сенсі нам потрібен «owned shared reference». Виявляється, у Rust є тип, який саме для цього підходить: `Arc`.

## `Arc` поспішає на допомогу

`Arc` означає **atomic reference counting** (атомарний підрахунок посилань).\
`Arc` обгортає значення й відстежує, скільки references на нього існує.
Коли останній reference знищується, пам'ять, виділена під значення, звільняється.\
Значення, обгорнуте в `Arc`, є immutable (незмінюване): ви можете отримати на нього лише shared references.

```rust
use std::sync::Arc;

let data: Arc<u32> = Arc::new(0);
let data_clone = Arc::clone(&data);

// `Arc<T>` реалізує `Deref<T>`, тож `&Arc<T>` можна перетворити
// на `&T` завдяки deref coercion (автоматичне розіменування до потрібного типу)
let data_ref: &u32 = &data;
```

Якщо у вас виникло відчуття дежавю, то недарма: `Arc` дуже схожий на `Rc` — reference-counted pointer, з яким ми
познайомилися, коли говорили про interior mutability. Різниця в потокобезпечності: `Rc` не є `Send`, а `Arc` — є.
Уся справа в тому, як реалізовано reference count: `Rc` використовує «звичайне» ціле число, а `Arc` —
**атомарне** ціле число, яке можна безпечно спільно використовувати й змінювати з різних потоків.

## `Arc<Mutex<T>>`

Якщо поєднати `Arc` із `Mutex`, ми нарешті отримаємо тип, який:

- Можна передавати між потоками, бо:
    - `Arc` є `Send`, якщо `T` є `Send`, і
    - `Mutex` є `Send`, якщо `T` є `Send`.
    - `T` — це `Ticket`, а він є `Send`.
- Можна клонувати, бо `Arc` є `Clone` незалежно від того, яким є `T`.
  Клонування `Arc` збільшує reference count, а дані не копіюються.
- Можна використовувати для зміни обгорнутих даних, бо `Arc` дає змогу отримати shared
  reference на `Mutex<T>`, через який, своєю чергою, можна захопити lock.

Тепер у нас є все потрібне, щоб реалізувати стратегію блокувань для нашого сховища тікетів.
